### 1.1 共有コード

相性計算(`compatibility.ts`)と型(`types.ts` の `MbtiType` / `AgeBand` / `Hobby` / `Rank` 等)は
リポジトリ直下の `shared/` に移動し、**Expoアプリと Worker の両方が同一実装をimport**する。
これにより相性スコアの計算結果がクライアント表示とサーバー判定でズレることを構造的に防ぐ。

```
shared/
  types.ts            # ドメイン型(既存 src/types.ts から移動)
  compatibility.ts    # 相性ロジック(既存 src/logic/compatibility.ts から移動)
backend/
  src/index.ts        # Hono エントリ
  src/routes/         # ルート定義(auth, me, venues, checkins, people, likes, chats, location)
  src/db/schema.ts    # Drizzle スキーマ
  src/db/migrations/  # drizzle-kit 生成
  wrangler.toml
```

## 2. 認証・ユーザー識別(匿名デバイスID)

ニックネーム・性別・連絡先を一切収集しない匿名設計。

1. 初回起動時、アプリは `POST /auth/register` にプロフィール(年代・趣味・MBTI)と
   **20歳以上の自己申告フラグ**を送信する
2. サーバーは `userId`(UUID)と**ランダムトークン**(256bit)を発行して返す。
   DB にはトークンの SHA-256 ハッシュのみ保存する
3. アプリは `userId` とトークンを端末の SecureStore に保存し、
   以降のすべてのリクエストに `Authorization: Bearer <token>` を付与する
4. トークン紛失(アプリ削除)= アカウント消失。再登録で新規ユーザーになる(MVP仕様)

- `ageConfirmed: true` でない登録は 400 で拒否する
- 本人確認・年齢確認書類・通報/ブロックは MVP 対象外(§10)。ただしテーブル追加だけで
  導入できるよう、users を中心とした正規化構成を保つ

## 3. データベーススキーマ(D1)

```sql
CREATE TABLE users (
  id            TEXT PRIMARY KEY,          -- UUID
  token_hash    TEXT NOT NULL UNIQUE,      -- SHA-256(token)
  age_band      TEXT NOT NULL,             -- '20代前半'|'20代後半'|'30代'|'40代'|'50代以上'
  mbti          TEXT NOT NULL,             -- 16タイプ
  created_at    INTEGER NOT NULL           -- epoch ms
);

CREATE TABLE user_hobbies (
  user_id  TEXT NOT NULL REFERENCES users(id),
  hobby    TEXT NOT NULL,                  -- 10種の趣味
  PRIMARY KEY (user_id, hobby)
);

CREATE TABLE venues (
  id        TEXT PRIMARY KEY,
  name      TEXT NOT NULL,
  category  TEXT NOT NULL,                 -- 'バー'|'居酒屋'|'カフェ'|'ラウンジ'
  lat       REAL NOT NULL,
  lng       REAL NOT NULL
);

CREATE TABLE checkins (
  id             TEXT PRIMARY KEY,
  user_id        TEXT NOT NULL REFERENCES users(id),
  venue_id       TEXT NOT NULL REFERENCES venues(id),
  checked_in_at  INTEGER NOT NULL,
  checked_out_at INTEGER                   -- NULL = 滞在中
);
CREATE UNIQUE INDEX idx_active_checkin
  ON checkins(user_id) WHERE checked_out_at IS NULL;   -- 1人1件のみ滞在中

CREATE TABLE likes (
  from_user  TEXT NOT NULL REFERENCES users(id),
  to_user    TEXT NOT NULL REFERENCES users(id),
  created_at INTEGER NOT NULL,
  PRIMARY KEY (from_user, to_user)
);

CREATE TABLE messages (
  id         TEXT PRIMARY KEY,             -- ULID(時系列ソート可能)
  from_user  TEXT NOT NULL REFERENCES users(id),
  to_user    TEXT NOT NULL REFERENCES users(id),
  text       TEXT NOT NULL,                -- 最大1000文字
  created_at INTEGER NOT NULL
);
CREATE INDEX idx_messages_pair ON messages(from_user, to_user, id);

CREATE TABLE user_locations (
  user_id    TEXT PRIMARY KEY REFERENCES users(id),
  lat        REAL NOT NULL,
  lng        REAL NOT NULL,
  updated_at INTEGER NOT NULL
);
```

- エリア定義は当面テーブル化せず、`shared/area.json` を単一の情報源として全コンポーネント
  (フロント・Worker・店舗インポートスクリプト)で共有する:
  `{ name: '国分町', lat: 38.2638, lng: 140.8699, radiusM: 300 }`
  (中心はOSMの夜間営業店舗151件の分布重心から算出)
- 店舗マスタ(venues)はマイグレーションのシードで投入する(モックの5店舗)

## 4. ドメインルール(サーバーで強制)

### 4.1 プレゼンス(エリア内判定)

- アプリはフォアグラウンド中、60秒間隔で `POST /location` に現在地を送る(心拍)
- **アクティブ** = `user_locations.updated_at` が現在から10分以内、かつ座標がエリア中心から
  `radiusM` 以内
- マップ・マッチ・店舗メンバー・プロフィール取得の対象は**アクティブなユーザーのみ**
  (仕様書「プロフィールは国分町エリア内にいる間だけ表示」のサーバー側強制)
- 非アクティブになったユーザーの滞在中チェックインは、参照時に無効として扱う
  (表示から除外。物理削除はしない)
- チャット(履歴・送信)はエリア外でも利用可能

### 4.2 相性

- スコア・ランクの算出式はアプリ仕様書 §4.4 の通り。`shared/compatibility.ts` を使用
- **サーバーが計算してレスポンスに含める**。クライアントは受け取った値を表示するだけ
- マッチ一覧は「自分以外のアクティブユーザー」を総合スコア降順に並べた上位N人(既定3)

### 4.3 チェックイン

- `POST /checkins` は滞在中チェックインがあれば自動でチェックアウトしてから作成する
  (同時に1店舗のみ)
- 店舗の「人数・MBTI分布・お店との相性%」は滞在中(かつアクティブ)のメンバーから算出。
  算出方法はアプリ仕様書 §4.5 と同じ(相性% = 自分と各メンバーの総合スコア平均、
  店舗MBTIキャラ = 最頻タイプ・同数はタイプ名昇順)

### 4.4 いいね・マッチ・チャット解禁

- **(A→B) と (B→A) の両方向の likes が存在 = マッチ成立**。チャット(閲覧・送信)はマッチ成立が必須
- 未マッチペアへの `GET/POST /chats/:userId/messages` は 403。`GET /chats` にもマッチ済みペアのみ表示
- 新規いいね時に `kind='like'` の通知メッセージを会話に自動投入(重複いいねでは投入しない)
- 受け取った未対応いいねは `GET /likes/received` で取得(マッチタブのバッジ・「いいねを返す」用)
- いいねは取り消し不可(MVP)。重複いいねは 200(冪等)

## 5. API仕様

- ベースURL: `https://<worker>.workers.dev`(カスタムドメインは運用時に設定)
- 認証: `POST /auth/register` 以外はすべて `Authorization: Bearer <token>` 必須。
  不正・欠落は 401
- ボディは JSON。エラーは共通形式:

```json
{ "error": { "code": "FORBIDDEN", "message": "チャットが解禁されていません" } }
```

code: `BAD_REQUEST` / `UNAUTHORIZED` / `FORBIDDEN` / `NOT_FOUND` / `CONFLICT` / `INTERNAL`

### 5.1 認証・プロフィール

| メソッド/パス | 説明 |
|---|---|
| `POST /auth/register` | 登録。`{ ageBand, hobbies[], mbti, ageConfirmed }` → `{ userId, token }` |
| `GET /me` | 自分のプロフィール → `{ userId, ageBand, hobbies[], mbti, checkin: { venueId, checkedInAt } \| null }` |
| `PUT /me` | プロフィール更新。`{ ageBand, hobbies[], mbti }`(部分更新不可・全項目送信) |

### 5.2 位置(心拍)

| メソッド/パス | 説明 |
|---|---|
| `POST /location` | `{ lat, lng }` → `{ inArea: boolean }`。60秒間隔で送信 |

### 5.3 店舗

| メソッド/パス | 説明 |
|---|---|
| `GET /venues` | 全店舗+集計。各要素: `{ id, name, category, lat, lng, distanceM, memberCount, mbtiCharacter, compatPct }`。distanceM は自分の最新位置から計算(位置未送信時は null) |
| `GET /venues/:id` | 店舗詳細: 上記+ `members[]`(滞在中アクティブメンバー、チェックイン古い順): `{ userId, mbti, ageBand, hobbies[], checkedInAt, compat: { total, rank } }` |

### 5.4 チェックイン

| メソッド/パス | 説明 |
|---|---|
| `POST /checkins` | `{ venueId }`。既存の滞在中は自動チェックアウト → `{ checkinId, venueId, checkedInAt }` |
| `DELETE /checkins/current` | 滞在中チェックインを解除。なければ 404 |

### 5.5 周辺・マッチ

| メソッド/パス | 説明 |
|---|---|
| `GET /people/nearby` | アクティブユーザー一覧(自分以外): `{ userId, mbti, ageBand, hobbies[], lat, lng, venueId \| null, compat: { total, rank } }`。座標は街歩き中のみ返す(店舗滞在中は venueId のみで座標は返さない) |
| `GET /people/:userId` | 相手プロフィール詳細(アクティブでない相手は 404)。チャット解禁済みの相手はエリア外でも取得可 |
| `GET /matches?limit=3` | 総合スコア降順の上位N人。要素は `/people/nearby` と同形 + `liked: boolean` |

### 5.6 いいね・チャット

| メソッド/パス | 説明 |
|---|---|
| `POST /likes` | `{ toUserId }` → 200。相互になった時点でマッチ成立 |
| `GET /likes/received` | 自分にいいねをくれた未対応の相手一覧: `{ userId, mbti, ageBand, hobbies[], compat }` |
| `GET /chats` | マッチ済み会話一覧: `{ peer: { userId, mbti, ageBand }, matched: true, lastMessage: { id, text, from, kind, createdAt } \| null }` |
| `GET /chats/:userId/messages?after=<messageId>` | メッセージ取得(kind: 'text' \| 'like')。`after` 指定時はそのID以降のみ(ULIDの辞書順)。省略時は直近100件。未マッチは 403 |
| `POST /chats/:userId/messages` | `{ text }`(1〜1000文字)→ 作成したメッセージ。未マッチは 403 |

## 6. ポーリング設計(クライアント側規約)

| 画面 | 取得API | 間隔 |
|---|---|---|
| マップ | `GET /venues` + `GET /people/nearby` | 10秒 |
| 店舗詳細 | `GET /venues/:id` | 10秒 |
| マッチ一覧 | `GET /matches` | 15秒 |
| チャット一覧 | `GET /chats` | 10秒 |
| トーク画面 | `GET /chats/:userId/messages?after=<最終id>` | 3秒 |

- 将来 Durable Objects + WebSocket に移行する場合も、これらの取得APIを初期ロードに
  そのまま使い、差分配信のみWebSocketに置き換える
- メッセージIDに ULID を使うのは `after` カーソルを時系列比較可能にするため

## 7. アプリ側の移行(モック → API)

画面は `src/api/client.ts` のみに依存しているため、この層の中身を fetch に差し替える。
関数とエンドポイントの対応:

| client.ts | エンドポイント |
|---|---|
| `completeProfile()` | `POST /auth/register`(初回)/ `PUT /me`(編集) |
| `useVenues` / マップ集計 | `GET /venues` |
| `usePeople`(walkers) | `GET /people/nearby` |
| `useMatches` | `GET /matches` |
| `checkIn` / `checkOut` | `POST /checkins` / `DELETE /checkins/current` |
| `sendLike` | `POST /likes` |
| `useChats` / `useChatMessages` | `GET /chats` / `GET /chats/:userId/messages` |
| `sendMessage` | `POST /chats/:userId/messages`(ダミー自動返信は削除) |
| (新規) | `POST /location` 心拍送信(フォアグラウンド60秒間隔) |

- 相性ランク・スコアはサーバー値を表示する(クライアント側計算は撤去。
  `shared/compatibility.ts` はサーバーが使用)
- ローカルzustandは「サーバーレスポンスのキャッシュ+ポーリング更新」の置き場になる

## 8. セキュリティ・運用

- レート制限: Cloudflare ダッシュボードの WAF Rate Limiting ルールで運用時に設定
  (Workerコード外)。目安: 書き込み系 30req/分、読み取り系 300req/分
- 入力検証: 全エンドポイントで zod によるスキーマ検証(年代・趣味・MBTIは列挙値のみ許可)
- メッセージは平文保存(MVP)。E2E暗号化は対象外
- CORS: アプリはネイティブのため不要。web版モック用に開発環境のみ許可
- 環境: `wrangler.toml` で dev / production の2環境。D1もそれぞれ別DB
- ログ: 個人特定につながる位置情報・本文はログ出力しない

## 9. テスト方針

- vitest + `@cloudflare/vitest-pool-workers` で実D1(ローカル)を使ったAPIテスト
- 必須ケース:
  - 登録 → Bearer 認証 → `GET /me` の往復
  - `ageConfirmed: false` の登録拒否
  - チェックインの排他(2店舗目で自動チェックアウト、UNIQUE制約)
  - プレゼンス期限切れ(10分経過)でマップ・マッチ・店舗から消えること
  - 片方向いいねでチャット解禁、未解禁ペアの送信 403
  - `after` カーソルでの差分取得
  - 相性スコアが `shared/compatibility.ts` の期待値と一致(既存ユニットテストを共用)
